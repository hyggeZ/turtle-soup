# 房间断线重连退避

## 问题与改动

房间页原来每 2 秒重连一次 WebSocket；断线时每 10 秒发一次 HTTP 补查。若许多客户端同时断线或服务端达到连接上限，请求会按相同节奏集中到达。

现在 WebSocket 重连从约 2 秒起步，连续失败时逐级增加到最多 30 秒，并在每次重连时加入 75%–125% 的随机抖动。连接稳定 30 秒后才清除连续失败次数，避免“刚连上又断开”反复退回 2 秒。离线 HTTP 补查改为随机 30–60 秒；连接正常时仍每 60 秒校准快照。若 WebSocket 还在但 HTTP 快照读取失败，则从约 10 秒开始带抖动地逐级退避，最多 60 秒；期间的 WebSocket 变更通知不再触发额外补查，成功读取后重置。离开房间、切换账号或房间关闭时会清理重连和补查定时器。

定时补查等本次快照请求完成后才安排下一次，快照 GET 最多等待 15 秒，避免慢请求不断叠加。这项改动只调整客户端请求时机，不改变房间状态、身份权限和服务端 WebSocket 协议。浏览器 WebSocket 不能直接读取失败握手中的 HTTP 错误正文，客户端因此对断线统一退避。

## 可复现测量

`cd web && npm test` 使用固定随机种子模拟 1000 个客户端同时断线，并假定所有重连立即失败、持续 60 秒。旧版按固定 2 秒重连和 10 秒补查；新版调用实际的延迟计算函数。统计 60 秒内请求总数与任意 100 毫秒窗口的最大请求数。

| 模拟请求 | 旧版总数 | 新版总数 | 旧版峰值 / 100 ms | 新版峰值 / 100 ms |
| --- | ---: | ---: | ---: | ---: |
| WebSocket 重连 | 30,000 | 4,670 | 1,000 | 112 |
| 离线 HTTP 补查 | 6,000 | 1,000 | 1,000 | 9 |
| WebSocket 仍在、HTTP 持续失败 | 6,000 | 2,065 | 1,000 | 30 |

模拟中重连次数减少约 84.4%，100 毫秒峰值减少 88.8%；离线 HTTP 补查次数减少约 83.3%，峰值减少 99.1%；连接尚在但 HTTP 持续失败时，补查次数减少约 65.6%，峰值减少 97.0%。这些是**定时策略的确定性模拟结果**，并非线上吞吐量或真实网络压测。持续故障时单客户端 WebSocket 恢复探测可能由固定最多 2 秒变为最多 30 秒，HTTP 补查也可能延后到 60 秒，这是减少请求洪峰的代价；连接和快照恢复后会重置对应退避。

`npm test` 的 5 个测试和 `npm run build` 均通过。服务端连接容量、实际批量断线后的数据库查询率和用户可感知恢复时间，需要在下一项服务端容量优化中单独压测。
