# WebSocket 连接容量限制

## 行为

房间连接在 WebSocket 升级前预留名额。单账号在同一房间最多 3 条、在同一服务进程最多 12 条连接。房间最多 128 条连接，其中非主持连接最多 125 条，按旁观者身份准入的连接最多 64 条。单进程最多 1024 条，其中非主持最多 960 条，按旁观者身份准入的最多 768 条。连接名额包含正在握手和已经建立的连接。房间满返回 `429 ROOM_LIVE_FULL`，进程满返回 `503 LIVE_CAPACITY_EXHAUSTED`，并给出 `Retry-After`。关闭的房间拒绝新连接。

握手在房间共享锁内读取主持与成员身份，再用互斥锁检查并预留名额。事务在升级前结束，拒绝分支先释放数据库锁再写 HTTP 响应。只有握手完成且名额仍有效才将用户记为在线。握手失败、断线和会话撤销释放名额。更换主持后同步数据库里的现任主持，提升其已有连接的类别并断开旧主持的连接，旧主持可以按现有成员身份重连。连接主动取消后仍有短暂的调度和关闭时间，内核套接字计数可能与名额计数短暂不同。

## 本地实测

用实际的本机 WebSocket 客户端、Go 测试 HTTP 服务和 Docker PostgreSQL 16 交替跑 3 轮旧版 `6041d67` 与新版。每轮使用独立测试进程和数据库 schema，128 个不同账号以旁观者身份向同一个等待房发起握手，最多 16 个并发拨号。连接稳定后用 1 秒加速心跳观察 3.3 秒，统计会话查询；堆增量和 goroutine 包含同进程的客户端和服务端。下表为三轮中位数。

| 指标 | 旧版 | 新版 |
| --- | ---: | ---: |
| 接受 / 拒绝 429 | 128 / 0 | 64 / 64 |
| 心跳会话查询/秒 | 121.52 | 65.45 |
| 客户端与服务端合计 Go 堆增量 | 4,567,256 B | 3,091,424 B |
| 客户端与服务端合计 goroutine 增量 | 384 | 198 |
| 接受连接的拨号 P50 | 14.941 ms | 32.253 ms |
| 接受连接的拨号 P95 | 90.826 ms | 126.663 ms |
| 128 次拨号阶段总用时 | 227.588 ms | 310.944 ms |
| 拨号阶段 pgx SQL 开始次数 | 384 | 704 |

在这个限额场景，心跳查询减少 46.1%，合计堆增量减少 32.3%。新版拒绝拨号 P50 为 12.800 ms。额外的房间锁读和事务增加握手开销，而且两个版本成功连接的样本数不同。新版三轮的成功拨号 P50 为 26.954、32.253、56.135 ms，连接池累计取连接等待 639.578 至 2,053.080 ms。另有一轮将 256 名旁观者平均分到 4 个房间，256 条都建立成功。

生产心跳为每 25 秒一次，128 条持续连接约对应 5.12 次会话查询/秒，64 条约 2.56 次/秒。这个换算假设连接稳定且各连接心跳分散。实测数字适用于单房旁观者被限额的场景，生产资源用量需结合线上连接分布。进程级上限由边界测试验证。这里限制的是实时连接，HTTP 快照读取和持久化房间成员另有自己的权限与资源边界。

## 回归

在独立 PostgreSQL 数据库运行 `go test ./... -count=1`。准入、会话撤销和主持状态用例通过 `go test -race ./internal/room -run '^(TestLiveHub|TestEvictedPending|TestLiveAdmission|TestPendingHost|TestSyncApprovedHost|TestLiveSession|TestLiveDisabledUser)' -count=1`。握手等待主持更换、回调乱序、已驱逐的预留连接无法激活三项再用 `-race -count=5` 验证。测试覆盖账号、房间和进程名额，429/503，升级失败释放，待握手主持无法开局，旧主持断开与新主持名额。
