# 第 342 条 WebSocket 背压

`liveHub` 给每条实时连接一个容量为 1 的通知通道。房间变化时尝试写入一条提示，通道已满就合并本次提示，发起通知的请求无需等待客户端读取。WebSocket 只发送 `changed`，客户端通过带游标和权限检查的 HTTP 快照追赶实际事件。[房间快照接口契约](38-房间快照接口契约.md)

每条连接独立写入。生产写入上下文最多等待 5 秒，失败退出时清理所在房间及全进程的连接名额。回收发生在连接循环退出后。应用层每条连接最多同时有一个写入中的提示和一个通道中的待处理提示，内核发送缓冲区有自己的空间预算。[WebSocket 写入接口](https://pkg.go.dev/github.com/coder/websocket@v1.8.15#Conn.Write)

## 进程内基准

连续执行 10,000 次广播。两条快速连接每轮在广播返回后读取，分别收到 10,000 次通知。慢连接整轮只保留 1 条，合并其余 9,999 次，恢复读取后也能接收下一轮通知。包含新用例的 Hub 测试连续通过 20 轮。

下面是 Windows/amd64 单 CPU 测量，每组 200 ms、重复 7 轮。计时范围包含一次广播和读取端消费本轮信号。

| 房间连接数 | 消费方式 | 每轮收到 | 每轮合并 | 单轮耗时中位数 | 单轮分配 |
| ---: | --- | ---: | ---: | ---: | ---: |
| 16 | 全部读取 | 16 | 0 | 0.706 µs | 0 B |
| 16 | 一半停读 | 8 | 8 | 0.413 µs | 0 B |
| 128 | 全部读取 | 128 | 0 | 5.255 µs | 0 B |
| 128 | 一半停读 | 64 | 64 | 3.247 µs | 0 B |

一半停读时测量包含更少的入队与读取操作。数据衡量应用内通知通道的成本，不代表 WebSocket 网络吞吐或整个连接的内存占用。

```powershell
go test -mod=readonly -count=20 -run '^TestLiveHub' ./internal/room
go test -mod=readonly -run '^$' -bench '^BenchmarkLiveHubNotifyBackpressure$' -benchmem -benchtime=200ms -cpu=1 -count=7 ./internal/room
```

## 写入阻塞回归

让真实 Gin 路由连接隔离 PostgreSQL 16，两个 WebSocket 客户端通过本机 TCP 完成握手。测试在慢连接的 I/O 层阻塞服务器的消息写入，直到生产代码真正关闭底层连接。故障夹具没有自己的回收定时器。这验证应用处理阻塞写入的路径，内核发送缓冲区饱和与广域网拥塞需要另测。

| 指标 | 5 轮观测 |
| --- | ---: |
| 阻塞期间广播 10,000 次 | 0.540–1.740 ms |
| 慢连接峰值待处理提示 | 1 条 |
| 健康连接逐条确认 | 每轮收到 4 条，最慢一次 1.360 ms |
| 从底层写入阻塞到关闭 | 5.001–5.022 s |
| 从底层写入阻塞到名额由 2 降至 1 | 5.001–5.112 s |

本项保留原本的有界缓冲与 5 秒写超时。独立回归覆盖从 0 个增至 2 个，生产路径的代码和运行开销沿用原实现。测试不测量整个进程的堆内存，也未提高连接容量。

设置隔离库的 `TEST_DATABASE_URL` 后可复测写入阻塞回归。

```powershell
go test -mod=readonly -v -count=5 -run '^TestLiveBlockedWriteReleasesCapacityWithPostgres$' ./internal/room
```
