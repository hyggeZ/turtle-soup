# 技术词典 1–100 项适用性评估

按《技术词典_频率排行.md》原序，结合现有 Go/Gin + PostgreSQL + Vue/WebSocket + 百炼 Qwen 项目判断。“接受（现有）”指代码已有对应能力，“接受（候选）”只是可安排实验；任何候选都须先有基线、再改动、验收与记录。现有 AI 主持是**单次受约束模型判定**，不能把它描述成具备工具循环、多 Agent 协作或 RAG 的系统。

## 1–50

| 序号 | 词条 | 判断 | 项目落点、前置条件或不引入原因 |
| ---: | --- | --- | --- |
| 001 | AI Agent | 改良 | 单人模式由 Qwen 判定问答/还原，当前无自主计划、工具调用和循环；简历应准确称“AI 主持”，未来 Agent 化需真实新任务。 |
| 002 | Python | 暂不 | 服务端已选 Go；离线评测/数据分析可用 Python，但不要为技术栈完整另起重复 API。 |
| 003 | LLM | 接受（现有） | 百炼 Qwen 参与单人主持判定；Go 校验枚举、计费、超时与持久化，不把模型回答直接当业务真相。 |
| 004 | RAG | 暂不 | 每局已有固定汤底和历史，外部检索会引入不可靠线索；若做相似题搜索再定义检索任务。 |
| 005 | Java | 不适用 | 项目是 Go 后端；不因岗位常见 Java 就在同一项目双写。 |
| 006 | Tool Calling | 暂不 | 主持只返回“是/否/无关”等枚举，不调用可执行工具；先有明确受控动作再设计工具权限。 |
| 007 | 算法 | 接受（现有基础） | 事件游标、房间轮次和排名/筛选涉及顺序与复杂度；性能优化要结合真实数据和基准。 |
| 008 | 数据结构 | 接受（现有基础） | `liveHub` 用 map 和有界 channel 维护连接；选型需兼顾并发锁、容量与过期回收。 |
| 009 | Redis | 实测后暂缓 | 线上四轮采样未找到稳定的热读瓶颈。保留 PostgreSQL，等数据量或连接池等待持续上升后复测 [判定依据](../19-Redis公开题目热读评估.md)。 |
| 010 | MySQL | 不适用 | PostgreSQL 已承载事务和迁移；没有双数据库的业务必要。 |
| 011 | MCP | 暂不 | AI 主持目前无外部工具；仅在为创作者/运营接入独立工具服务且需要互操作时考虑。 |
| 012 | 分块 | 不适用 | 汤面、汤底是短文本，不做长文档 RAG；硬切会破坏谜题语义。 |
| 013 | C++ | 不适用 | 无原生高性能模块或推理内核；Go 已能承担 HTTP/WebSocket 工作。 |
| 014 | Docker | 接受（现有） | `compose.yaml` 启动本地 PostgreSQL；容器化后端可作为发布实验，不把 Docker 当成不可信代码沙箱。 |
| 015 | FastAPI | 不适用 | 无 Python API 服务；Go/Gin 已定义权限与状态机。 |
| 016 | Spring Boot | 不适用 | 项目不运行 Java 服务。 |
| 017 | 幂等性 | 接受（现有） | 房间操作 ID 与请求摘要、AI 用量等使用 PG 唯一约束；要继续验重复/超时重试和同键不同载荷。 |
| 018 | Go | 接受（现有） | Gin 处理 HTTP，goroutine/WebSocket 处理连接，PG 事务管状态；优化聚焦内存、锁、连接与取消。 |
| 019 | Agent Skills | 不适用 | 玩家 AI 主持没有可加载技能包；开发助手技能不能算入产品功能。 |
| 020 | Git | 接受（现有工程） | 每项可验收优化独立提交，保留基线、回归与性能报告；提交历史只证明真实改动。 |
| 021 | SQL | 接受（现有） | pgx 显式 SQL 处理事务、关系与分页；用实际执行计划判断慢查询和索引。 |
| 022 | Multi-Agent | 暂不 | 海龟汤主持无需多个 Agent 分工；只有出现创作、审核等独立任务并证实收益时再研究通信。 |
| 023 | Reranker | 暂不 | 尚无检索候选和相关性标签；“题目推荐”定义后再评估重排。 |
| 024 | Workflow | 接受（现有） | 真人对局按等待、进行、暂停、结束和角色规则执行确定性流程；不需要 Agent 编排框架。 |
| 025 | SSE | 暂不 | 房间已有双向 WebSocket，AI 判定返回短 JSON；单向长任务出现后再试 SSE。 |
| 026 | Lua | 暂不 | 当前无 Redis 原子脚本或 OpenResty 规则；PG 事务已解决关键状态一致性。 |
| 027 | MyBatis | 不适用 | Java SQL 映射框架；Go 使用 pgx。 |
| 028 | 超时 | 接受（现有） | Qwen 客户端、房间 HTTP 操作、WebSocket 写入已有超时；继续核对 Context 取消沿链路传播。 |
| 029 | 量化 | 不适用 | Qwen 模型由百炼托管，应用无法调整权重位宽或证明量化收益。 |
| 030 | LangChain | 不适用 | 单次 Qwen 判定用 Go 直接调用即可；无 Python Agent 工作流。 |
| 031 | ReAct | 不适用 | 无思考—工具—观察循环；主持只做受限分类，不应包装成 ReAct。 |
| 032 | Embedding | 暂不 | 题库暂无语义搜索；先有已标注的检索需求，比较关键词基线和向量收益。 |
| 033 | Fallback | 接受（现有） | 百炼不可用时回放已完成操作，新判定明确提示不可用，保留状态 [离线重放](../13-AI操作离线重放.md)。 |
| 034 | Hybrid Retrieval | 暂不 | 只有题库搜索场景与评测集建立后，才比较关键词+向量召回。 |
| 035 | 消息队列 | 暂不 | 当前房间事件先写 PG，WebSocket 只发变更提示；异步通知/审核积压后再定义队列语义。 |
| 036 | Linux | 接受（现有工程） | 服务器部署与 systemd/Nginx 在 Linux；排障应掌握进程、端口、文件权限和日志。 |
| 037 | BM25 | 暂不 | 尚无题目全文搜索；需求出现后先与 PostgreSQL FTS 及人工标签对照。 |
| 038 | LangGraph | 不适用 | 没有多步 Agent 状态图，游戏状态已由 Go+PG 管理。 |
| 039 | Worker Pool | 实验后撤回 | 候选限制 AI 峰值并发，但普通接口收益不稳定，压测时 24 次请求中 16 次被拒绝 [对照数据](../20-AI判定并发隔离实验.md)。 |
| 040 | 缓存穿透 | 暂不 | 尚无 Redis 缓存；引缓存后若无效公开 ID 导致反复回源，再用短空值缓存，不能缓存权限拒绝。 |
| 041 | 限流 | 接受（现有） | 注册/登录、发布和房间连接已有额度与 429；多实例时需重新评估共享限额。 |
| 042 | Prompt Engineering | 接受（现有） | 两类判定提示词有版本和受限 JSON 输出；改提示词须用冻结题集比较误判与 Token。 |
| 043 | Trace | 接受（现有） | 后台展示按起点排序的相对时间线、阶段耗时、失败和日志占用，已以真实请求核对 [上线回归](../18-上线回归与性能基线.md)。 |
| 044 | 分布式锁 | 不适用 | 单服务关键状态以 PG 行锁/唯一约束保证；Redis 锁会引入租约与围栏问题。 |
| 045 | C | 不适用 | 无 C 原生组件或内核开发。 |
| 046 | AOP | 接受（概念） | Gin 中间件横切处理追踪、同源校验等；不需要 Spring AOP 或动态代理。 |
| 047 | MyBatis-Plus | 不适用 | Java ORM 插件，与 Go/pgx 无关。 |
| 048 | RRF | 暂不 | 无多路检索结果可融合；题库搜索与标注集建立后再实验。 |
| 049 | SQLite | 不适用 | PostgreSQL 是唯一真源，集成测试也应用真实 PG 验证锁语义。 |
| 050 | 延迟分位数 | 接受（现有） | 后台统计路由 P95，AI 评测有 P50/P95；报告须标明样本量、负载和错误率。 |

## 51–100

| 序号 | 词条 | 判断 | 项目落点、前置条件或不引入原因 |
| ---: | --- | --- | --- |
| 051 | Dense Retrieval | 暂不 | 尚无相似汤题搜索；若上线，先标注相关性和权限过滤再比较向量召回。 |
| 052 | JavaScript | 接受（现有） | Vue 组件与前端 API 使用 JS；应保持请求处理、状态更新和计时逻辑清晰可测。 |
| 053 | TypeScript | 接受（已实施） | 历史事件和重连计时使用严格 JSDoc 类型检查，放入前端构建，不增加发布资源 [验证数据](../21-房间历史与重连类型检查.md)。 |

| 056 | 滑动窗口限流 | 暂不 | 现用固定时间窗；若窗口边界突发产生实际风险，再对比更平滑的滑动窗与额外状态成本。 |

| 060 | Checkpoint | 改良 | 对局事件/状态已存 PG 并可重连恢复；这是业务持久化，不是 LangGraph Agent Checkpointer。 |

| 062 | TTL | 接受（现有） | 会话及单进程限流状态需要过期回收；未来缓存 TTL 还要与业务变更主动失效配合。 |
| 063 | 补偿事务 | 暂不 | 当前关键操作同一 PG 事务提交，没有跨服务 Saga；引外部不可回滚副作用后再设计补偿。 |
| 064 | 降级 | 改良 | 与第 33 项同一项：AI 不可用时保持状态可恢复并明确告知，避免伪造主持判定。 |

| 066 | MVCC | 接受（基础） | PostgreSQL 通过 MVCC 支持并发读写；房间“不能超员”仍需行锁/约束，不靠 MVCC 自动成立。 |
| 067 | PostgreSQL | 接受（现有） | 账号、题目、房间、事件和 AI 配额都以 PG 为权威；事务、约束、索引和备份是重点。 |
| 068 | 任务状态机 | 接受（现有） | 房间等待、进行、暂停、结束及 AI 对局有确定转换；越权/重复事件必须由后端拒绝。 |
| 069 | 吞吐 | 接受（候选） | 对固定场景报告成功请求/秒与错误率；AI 另报 Token 与额度，不能只用峰值 QPS。 |
| 070 | 长期记忆 | 暂不 | 跨局记住玩家/题目会泄露汤底且增加偏见；当前只需本局持久历史和有限上下文。 |
| 071 | Transformer | 接受（基础） | 认识 Qwen 底层模型结构即可；项目不实现 Transformer 网络。 |
| 072 | SFT | 暂不 | 需要合规标注数据、可训练模型和留出集；先证明提示词/规则与模型选型无法满足目标。 |
| 073 | 分布式追踪 | 改良 | 当前是单服务请求 trace，不应称跨服务分布式追踪；未来服务拆分再做 Trace Context 跨进程传播。 |
| 074 | 沙箱 | 不适用 | 玩家和模型都不提交可执行代码；Docker 数据库容器不是代码执行沙箱。 |
| 075 | Hit@K | 暂不 | 没有检索候选集与标注相关题，无法计算有意义的命中率。 |
| 076 | MRR | 暂不 | 同上，只有题库搜索/排序目标确定后才有排名指标。 |
| 077 | Qwen | 接受（现有） | 单人主持使用百炼 Qwen 兼容 API；固定模型版本、温度、提示词和输出校验以便回归。 |
| 078 | REST | 接受（现有） | 账号、题目、房间操作通过 HTTP JSON；WebSocket 仅通知变化，私有状态由权限校验接口获取。 |

| 081 | 微服务 | 暂不 | 现有内部模块与单库能保持事务和房间实时性；独立扩缩/团队边界出现后再拆。 |

| 087 | DeepSeek | 暂不 | 可作候选模型对照，但必须用同题集比较错误通关、延迟、费用及数据合规后才替换/路由。 |

## 优先落地点

先完成第 43/83/73 项当前单服务的追踪与取消传播；第 55/86/100 项在固定 AI 题集上做质量与长局实验；第 9 项 Redis 仅在第 69/96 项证实公开读瓶颈后实施。多 Agent、RAG、微服务、消息队列、量化均应由明确功能/资源边界触发，不能作为当前阶段的装饰项。
