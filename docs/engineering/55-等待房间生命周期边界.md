# 第 397 条 等待房间生命周期边界

作者删除题目和管理员隐藏题目都会关闭关联的等待房间。两条路径此前各维护一份房间加锁与关闭 SQL。现在由房间模块提供 `LockWaitingBySoup` 和 `CloseWaitingBySoup`，两条入口各自持有原来的 PostgreSQL 事务。

房间模块按 ID 锁定等待房间，并只关闭仍处于 `waiting` 的房间。两条入口先锁等待房间，再锁题目。持有题目锁后以 `NOWAIT` 补查期间新建的等待房间，遇到锁冲突由调用方回滚、退避并重试。[PostgreSQL 行锁语法](https://www.postgresql.org/docs/16/sql-select.html#SQL-FOR-UPDATE-SHARE)

作者权限、后台审核与审计、重试策略由各自入口处理。关闭操作返回房间 ID，通知仍在事务提交后发出。已经开始的对局保留原题目快照。

## 前后对照

用固定基线 `fb243ae` 与候选分别运行实际 Gin 路由，连接隔离 PostgreSQL 16.15。每次请求使用新题目，关联一个等待房和一个进行中房间。两版交替执行三对，每个入口每组预热 2 次、正式记录 18 次，共 216 个正式请求。统计包含认证、事务和 HTTP 处理。时延取各组分位数的中位数。

| 入口 | 两版响应 | SQL 次数（旧→新） | P50（旧→新） | P95（旧→新） |
| --- | --- | --- | ---: | ---: |
| 作者删除题目 | `204` | 9 → 9 | 169.131 → 177.785 ms | 298.770 → 411.479 ms |
| 后台隐藏题目 | `200`，关闭 1 间 | 10 → 10 | 197.619 → 192.086 ms | 312.241 → 350.234 ms |

同一入口的 SQL 文本与顺序在两版逐条一致，全部正式请求只关闭与通知等待房。每批只有 18 个样本，该批 P95 即最大值。两版延迟区间重叠，逐对变化方向不同，当前数据不足以判断稳定的延迟变化。数据库通过 SSH 隧道连接。

社区、后台、房间三个 Go 包共执行两轮定向回归。建房与删题或隐藏并发、换题持锁时的重试、只关闭等待房、审计失败回滚和汤底资格控制全部通过。

设置隔离库的 `TEST_DATABASE_URL` 后，可运行 `go test -v ./internal/admin -run '^TestWaitingRoomsMutationContract$'` 验证两条入口的响应、SQL 顺序、落库和通知。
