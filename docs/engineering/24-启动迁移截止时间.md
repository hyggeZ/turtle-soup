# 第 083 条启动迁移截止时间

服务会先连接 PostgreSQL、迁移表、恢复房间，再开始监听健康检查。原启动入口以无截止时间的 Context 运行迁移。数据库内已有事务占用迁移锁时，启动协程会一直等待。

启动入口现在给整个迁移阶段 10 秒预算，并将带截止时间的 Context 传给连接池和迁移事务。超时沿用启动错误处理，进程退出后由现有服务配置重试。迁移仍在事务中，发布健康检查失败时仍走现有回滚流程。10 秒适用于随应用启动执行的迁移，大规模数据迁移需按实际规模单独排期。

## 实验与回归

在 Linux 服务器的独立 PostgreSQL 16 数据库，每轮分别建立空 schema，使用另一条连接持有迁移锁。基线由 `pg_locks` 确认可见等待后，再持锁约 450 ms。候选用 150 ms 测试预算走实际启动函数，保持锁占用直到函数自行返回。同一夹具运行 5 轮。

| 观察项目 | 实测 |
| --- | --- |
| 旧版保持阻塞 | 确认进入等待后再持锁 450.59–450.99 ms，5 轮都未返回 |
| 旧版在放锁后迁移成功 | 五轮总耗时中位数 559.259 ms，包含人工持锁时间 |
| 候选自动超时 | 150.553–150.705 ms，中位数 150.605 ms，5 轮均返回 `DeadlineExceeded` |
| 候选释放锁后重试 | 五轮中位数 112.679 ms，每轮均写齐第 1–16 版 |

候选超时时没有迁移版本表。另跑了服务包 6 项和迁移包 2 项回归，覆盖超时、WebSocket、健康检查、空库初始化和第八版升级。收益是启动等待有上限；实验未测正常请求延迟或吞吐，也未将 150 ms 当成线上配置。
