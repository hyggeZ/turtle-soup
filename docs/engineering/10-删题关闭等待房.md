# 题目下架时关闭等待房

## 问题与规则

作者删除题目后，旧实现只给题目标记 `deleted_at`，已使用该题的等待房仍保持 `waiting`。旧版真实 PostgreSQL 回归在删题后读到 `status=waiting, closed_at=NULL`。这类房间可从历史入口继续找到，且旧的开局操作没有再次核对题目状态。后台隐藏题目时也需要覆盖建房与换题同时发生的窗口。

现在作者删题、后台隐藏题目会在同一事务中关闭该题的所有等待房，并在提交后通知已连接的房间页面刷新。已开局的房间保留状态及题目快照，原成员可继续或回看；下架题目的房间不再进入招募大厅，也不接纳新成员。即使数据库中留有历史等待房，开局仍会重新校验题目是否可见。

## 并发处理

房间设置和入场按“房间行、题目行”取锁。删题与隐藏先锁已存在的等待房，再锁题目；题目锁取得后再次以 `FOR UPDATE NOWAIT` 扫描等待房。首轮扫描后若刚出现新房，且换题请求持有新房锁并等待题目锁，第二轮不能等待该房，否则形成锁循环。此时整笔事务回滚、短暂退避并重试；最多 16 次，耗尽返回 503。新建房间会在题目锁释放后重新检查下架状态。

两次扫描都使用现有等待房索引，无需新增迁移。房间关闭与题目下架一起提交，避免只完成其中一半。

## 验收

- 旧版真实 PostgreSQL 用例复现：作者删题后等待房仍是 `waiting`、`closed_at=NULL`，该用例失败。
- 新版真实 PostgreSQL 回归覆盖等待房关闭、WebSocket 刷新通知、进行中及已结束房间保留、原成员重连、新成员拒绝、大厅过滤、历史遗留等待房拒绝开局。
- 并发回归覆盖删题与建房、删题与开局、后台隐藏与建房，以及“首轮扫描后新房被设置请求锁住”的确定性窗口。后者验证回滚重试实际发生且最终无遗留等待房。
- `TEST_DATABASE_URL=... go test ./...` 全部通过；删题和后台隐藏的相关用例重复 3 次通过，`go test -race ./internal/forum ./internal/admin -run '^(TestDelete|TestHideSoup)' -count=1` 通过。

## 开销与局限

正常作者删题从 2 条数据库语句增加到 6 条：只读权限检查、两次等待房扫描、题目锁读、更新题目、关闭房间。后台隐藏从 5 条增加到 6 条。重复删除只做 1 条只读查询。大厅仍是一条查询，但会对候选房间联查题目可见性；开局增加一次题目主键锁读；入场没有增加数据库语句。增加的开销用于保证房间状态和权限一致，不能称作性能提升。

同机 Windows、Go 1.26.5、Docker PostgreSQL 16，使用独立临时 schema。每次新建一题、没有关联等待房；每轮先做 10 对预热，再交替执行旧版和新版各 100 次，共 3 轮。只计删题事务，不计题目插入与清理。旧路径按上一提交的 `BEGIN / SELECT FOR UPDATE / UPDATE / COMMIT` 原样执行，新路径调用当前 `Store.Delete`。这是**没有等待房时相同业务结果**的开销对照；有等待房时旧实现根本没有完成关闭，不能直接比较完成同一任务的速度。

| 指标 | 旧版三轮中位 | 新版三轮中位 | 变化 |
| --- | ---: | ---: | ---: |
| P50 | 6.330 ms | 11.405 ms | +5.075 ms |
| P95 | 17.034 ms | 26.110 ms | +9.076 ms |
| 业务 SQL 语句 | 2 | 6 | +4 |

这是一项**有测得耗时成本的正确性修复**：增加的锁检查保证删题与关房原子完成，并处理建房、换题和开局竞态。本机三轮 P50 分别为旧版 6.284/6.987/6.330 ms、新版 11.322/13.430/11.405 ms；P95 分别为旧版 17.034/17.224/12.793 ms、新版 24.717/40.479/26.110 ms。短时间本地测量有抖动，不能外推为生产延迟。高冲突场景未做生产规模压测；16 次重试用尽时需由客户端稍后再试。
