# 已结束房间历史分页

## 做法

网页进入房间时请求 `GET /api/rooms/:id?history=1`。已结束房间取最近 50 条原始事件，若回答对应的旧问题位于页外，一并返回，单页最多因此补入 50 条。较早页用 `?history=1&before=<historyBefore>` 查更小的事件 ID，`historyBefore=0` 表示结束。游标按原始事件计算，权限过滤后整页为空也可以继续翻页。首屏 `eventCursor` 是房间最大的原始事件 ID，可以用旧增量接口接收后续变化。较早页的 `eventCursor` 仅表示本页最大原始 ID。

房间身份、题目、成员和事件从同一个 PostgreSQL 只读快照读取。较早页按 ID 去重合并到网页，实时状态和实时游标由原有增量请求维护。离开房间或身份变化会取消旧页请求。已结束房间的快照和翻页继续按当前身份过滤汤底、未答问题和私人还原。已有全量接口可继续使用。进行中的房间仍读取完整快照，供主持待办和玩家动作判断使用。

## 本地实测

用 `TestReplayHistoryScale` 对同一房间交替请求全量、最近页和中段页。每轮分别准备 100、1,000、5,000 条已结束的房间事件，数据各半为问题和回答，问题先写、回答后写。最近页在每个规模都取 50 条回答，再回补其 50 条问题。用旁观账号调用 Gin 测试处理器和本机 Docker PostgreSQL 16，每个规模和路径预热 5 次、记录 30 次，共 3 轮。表内为每轮指标的中位数，字节数基于未压缩 HTTP 响应体。

| 原始事件 | 请求 | 响应字节 | P50 | P95 | pgx 操作/次 |
| ---: | --- | ---: | ---: | ---: | ---: |
| 100 | 全量 | 22,273 | 5.31 ms | 9.45 ms | 6 |
| 100 | 最近页 | 22,292 | 6.03 ms | 13.68 ms | 7 |
| 100 | 中段页 | 15,248 | 5.94 ms | 13.88 ms | 7 |
| 1,000 | 全量 | 218,693 | 10.37 ms | 22.63 ms | 6 |
| 1,000 | 最近页 | 22,571 | 7.49 ms | 31.01 ms | 7 |
| 1,000 | 中段页 | 15,369 | 6.56 ms | 17.22 ms | 7 |
| 5,000 | 全量 | 1,099,593 | 30.13 ms | 49.21 ms | 6 |
| 5,000 | 最近页 | 22,721 | 7.70 ms | 13.41 ms | 7 |
| 5,000 | 中段页 | 15,471 | 6.16 ms | 11.25 ms | 7 |

5,000 条事件时，首屏响应缩小 97.9%，P50 降低 74.4%。100 条事件时，最近页的回补覆盖了全部事件，多一次数据库操作使首屏 P50 略升。1,000 条事件的最近页 P95 在三轮中分别为 32.80、17.09、31.01 ms，尾延迟受本机抖动影响。延迟包含本地数据库及 JSON 生成，压缩后流量、生产网络耗时和浏览器渲染时间需另测。主动加载全部历史还会产生多次请求。

在 Windows PowerShell 设置 `TEST_DATABASE_URL` 为本地测试库连接串，然后运行：

```powershell
$env:REPLAY_HISTORY_SCALE = '1'
go test ./internal/room -run '^TestReplayHistoryScale$' -count=3 -v
```

回归覆盖跨页补题、全私有空页继续翻页、主持与旁观权限、旧全量与增量兼容、无效参数和进行中回退，前端测试覆盖事件去重和游标前进。
