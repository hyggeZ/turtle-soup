# 已结束房间的公开回看

## 问题与规则

原系统保存了已结束房间的过程，但只有原成员能读取。新用户用房间码加入时收到 409，公开房间列表也排除已结束房间，与规划中的公开回看不一致。

现在新增独立的公开回看列表，保留原招募大厅的含义；列表只返回房间概要、模式、状态、房间码和汤底公开状态，不返回汤底或事件。共探和竞答的已结束房间都可回看，新访客只以旁观者入场，重复入场保持幂等。私密房间不进入列表，新访客必须持有新的 32 位房间码；兼容旧版的 8 位私密码只允许原成员回看，避免短码被猜测。已关闭房间、已隐藏或删除题目的房间不向新访客开放，原成员的历史仍按原有入口读取。直接猜房间 ID 不能绕过成员检查。

回看沿用服务端快照过滤：未公开汤底仍为空，未答问题和他人的私人还原正文不会向新旁观者返回。汤底已公开时，入场在房间行锁之后获取题目行锁，检查该用户是否正在其他同题真人或单人 AI 对局；允许入场后记录 `soup_reveals`，阻止随后再以玩家身份参加同题。这与现有公开汤底和对局入场使用同一锁序。

## 验收

- 旧实现的真实 PostgreSQL 回归已复现：新访客用已结束房间码入场返回 409，公开回看接口不存在。
- 新增 7 个真实 PostgreSQL 测试：公开回看列表与原招募列表分离、51 间房间的游标翻页、公开/私密及新旧房间码、关闭与下架题目、旁观身份、未公开汤底和私人事件的全量/增量快照过滤、已公开汤底的同题资格限制。
- 回看入场与主持公开汤底、与单人 AI 开局的并发用例各重复 10 次通过，针对这两项的 `go test -race` 通过；未出现“读到汤底又保留同题玩家资格”的结果。本地 PostgreSQL 上 `go test ./... -count=1` 全部通过，`web` 的 `npm run build` 通过。

## 开销对照

同机 Windows amd64、Go 1.26.5、Docker PostgreSQL 16，每个场景固定 100 次、重复 3 轮。以下为本地观测的三轮中位数；旧路径只返回拒绝，新路径会写入旁观成员，**不是相同业务操作的速度对照**。

| 场景 | 中位耗时 | 数据库操作 / 请求 | 分配量 / 请求 | 分配次数 / 请求 |
| --- | ---: | ---: | ---: | ---: |
| 旧短私密码拒绝路径代理 | 6.984 ms | 5 | 约 11.46 KB | 106 |
| 新回看入场，汤底未公开 | 13.527 ms | 8 | 约 12.55 KB | 129 |
| 新回看入场，汤底已公开 | 25.450 ms | 10 | 约 13.10 KB | 140 |
| 50 条公开回看列表 | 2.772 ms | 1 | 约 130 KB | 2354 |

未公开入场增加成员写入和状态校验；已公开入场另增加同题资格查询和揭底记录。现有房间快照未改动，本次复测中位 9.358 ms、6 次数据库操作/请求。三轮本机耗时波动明显，不能把拒绝路径与成功写入路径的差值称作性能回退，也不能把小表执行计划外推到大型房间库。回看列表当前本地样本只有少量房间，后续房间量增长时再测分页查询和索引。
