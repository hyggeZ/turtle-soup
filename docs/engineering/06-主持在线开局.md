# 开局时确认主持在线

## 问题与修复

等待房间原来只检查已经指定主持人、至少有一名玩家，便允许房主或主持人开局。若主持在等待期间断线，房主仍可把房间变为进行中；原有断线暂停逻辑只处理已经开始的对局，因此这个房间会持续接受问题，却没有在线主持回答。

现在首次 `start` 在房间事务持有行锁时检查主持人的 WebSocket 在线状态。主持离线返回 409；主持在线才能开局。相同操作 ID 的已成功开局请求先从幂等记录返回原结果，即使主持后来断线也不误报失败。WebSocket 离线处理在另一个事务中更新房间：若断线发生在在线检查之后，会等待开局事务提交，再把进行中的房间暂停。实现不持有连接表的互斥锁去执行数据库查询。

这是当前单实例服务的在线判断；如果未来部署多个 Go 实例，需要共享在线状态或保证房间连接和操作进入同一实例，不能直接沿用进程内连接表。

## 验收与开销

- 旧实现的真实 PostgreSQL 用例复现：主持离线时 `start` 错误返回 200。修复后同一场景返回 409；连接主持 WebSocket 后开局成功，最后连接断开后房间暂停，暂停后的相同操作 ID 重试仍返回幂等结果。
- 既有共探、竞答及快照权限用例改用真实主持 WebSocket 连接，不为测试跳过在线校验。
- 本地 PostgreSQL 上 `go test ./... -count=1` 全部通过；`go test -race ./internal/room -run 'TestAnswerRevealAndRoomJoin|TestOldHostSnapshotDoesNotSeeNewPrivateRestore' -count=1` 通过。
- 首次开局增加 1 次进程内互斥锁与 map 查询，没有新增 SQL 或外部调用。独立微基准测得约 20–90 ns/op、0 B/op、0 allocs/op；本机波动较大，这只说明查询量级，不能当作端到端开局提速数据。该检查的收益是离线主持不能启动无主持对局。
