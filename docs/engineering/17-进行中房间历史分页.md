# 进行中房间历史分页

## 做法

新版网页用 `history=2` 请求最新一页，再用 `before` 向前查记录、用 `after` 追赶新事件。每次读取最多 50 条原始事件，回答需要时补出对应的旧问题。`historyBefore` 翻较早的历史，`eventCursor` 接续新事件，`tasks.nextAfter` 翻仍待处理的事项。可见结果为空时，事件游标仍按扫描到的原始 ID 前进。

服务端在同一个 PostgreSQL 只读快照中读取身份、成员、待办和事件，沿用同一套隐私过滤。此前的 `history=1` 仍是仅为已结束房间分页的协议，旧网页可以继续加载活跃房间的完整记录。未选择分页的接口也沿用原有全量和增量行为。

网页以串行请求处理实时增量。当前读取结束前收到的多条通知合成一次续读；服务端返回 `hasMoreNew=true` 时继续追赶。较早页只合并事件和较早页游标。切换房间、账号或身份时使旧读请求失效。同房间的事件写入先锁定房间行，再生成事件 ID 并提交，保证按游标读取时不会跨过尚未提交的同房间事件。

## 本地实测

`TestActiveHistoryScale` 使用真实 Docker PostgreSQL，在同一个进行中的房间写入 5,003 条事件，其中开头 3 条保持待办，其余 2,500 组问答先写问题、后写回答。首读用旧全量和新最近页对照，翻较早页使用实际网页参数。追赶用最后 500 条回答和它们对应的旧问题，比较旧版一次取完与新版每批 50 条原始事件。字节数为未压缩 JSON。追赶测量包括解析各批 JSON，且请求在本机连续发送。

快照各路径预热 5 次、记录 30 次；追赶预热 3 次、记录 20 次。各跑三轮，表中取每项指标的三轮中位数。

| 请求 | 响应字节 | P50 | P95 | pgx 操作/次 |
| --- | ---: | ---: | ---: | ---: |
| 旧活跃房首读 | 1,098,174 | 44.70 ms | 108.54 ms | 7 |
| 新活跃房首读 | 23,037 | 13.61 ms | 47.65 ms | 8 |
| 新活跃房较早页 | 15,394 | 7.72 ms | 33.38 ms | 7 |
| 旧空增量 | 1,017 | 10.43 ms | 26.30 ms | 7 |
| 新空增量 | 1,036 | 9.13 ms | 15.95 ms | 7 |

首读响应体缩小 97.9%，本机 P50 降低 69.6%。空增量跳过事件明细读取，两版都是 7 次 pgx 操作。空增量延迟波动较大，主要验证查询次数没有增加。

| 追赶 500 条原始事件 | 旧增量 | 新分页增量 |
| --- | ---: | ---: |
| 请求数 | 1 | 10 |
| 最大单次响应 | 221,016 B | 23,035 B |
| 总响应 | 221,016 B | 230,339 B |
| pgx 操作总计 | 7 | 80 |
| 全部追赶 P50 | 23.49 ms | 113.42 ms |
| 全部追赶 P95 | 34.81 ms | 149.07 ms |

追赶的最大单次响应缩小 89.6%，两种路径均获得 1,000 条去重后的问题与回答。分页增加请求数、重复元数据和完成全部追赶的时间。这里测的是本机 HTTP 处理器和 PostgreSQL，浏览器网络往返会增加实际用时。这些上限约束的是单次响应的事件数，成员列表和用户已主动加载的全部历史是另外的开销。

```powershell
$env:ACTIVE_HISTORY_SCALE = '1'
go test ./internal/room -run '^TestActiveHistoryScale$' -count=3 -v
```

运行前将 `TEST_DATABASE_URL` 设为本机测试库连接串。用例会创建并清理独立 schema。

真实 PostgreSQL 回归覆盖旧网页兼容、50／51 边界、`after=0`、空增量、过滤后空页继续追赶、旧问题回补、正在处理的早期待办，以及不同房间状态。前端测试覆盖通知合并、切视图失效和三个游标的独立处理。
