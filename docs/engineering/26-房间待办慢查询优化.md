# 第 096 条 房间待办慢查询优化

主持端查待办时，先用房间和待办游标定位问题、还原与看底申请，再判断有没有子事件结束这条待办。历史上的回答索引只收录 `answer`，无法支持这个不区分子事件类型的检查。

- 迁移 017 为 `parent_id IS NOT NULL` 的事件添加部分索引。原有回答索引继续服务只查询 `answer` 的路径。
- 主持待办查询单独使用 `pgx.QueryExecModeExec`。参数仍由 pgx 绑定，PostgreSQL 根据当前房间和待办游标构造执行计划。其他查询继续使用原来的 pgx 模式。

## 读路径对照

使用独立 PostgreSQL 16.15 测试库，默认 `plan_cache_mode=auto`。同库创建 50 对问答的短房间、各 5,000 对问答的两个长房间，以及 52 项待办的分页房间。执行 `VACUUM ANALYZE` 后依次测原实现、只改执行方式、只加索引、联合改动、原实现复测。每组真实 Gin 接口预热 3 次后采样 65 次，单条 SQL 预热 3 次后采样 25 次。测试进程通过本地套接字连接 PostgreSQL，接口计时包含 handler 和数据库事务。

| P95（ms，越低越好） | 原实现 | 仅按参数规划 | 仅加索引 | 联合改动 | 原实现复测 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 短局，无待办，主持接口 | 5.91 | 6.20 | 7.15 | 4.79 | 6.22 |
| 长局，有待办，主持接口 | 7.04 | 8.08 | 6.40 | 4.67 | 6.98 |
| 短局，无待办，主持 SQL | 2.25 | 2.30 | 3.22 | 0.63 | 1.98 |
| 长局，无待办，主持 SQL | 7.03 | 6.80 | 4.99 | 3.38 | 6.42 |
| 长局，有待办，主持 SQL | 6.38 | 6.87 | 5.06 | 3.83 | 6.18 |
| 长局，有待办，玩家 SQL | 4.37 | 3.62 | 0.79 | 0.79 | 3.62 |

首轮原实现、仅加索引、原实现复测的短局主持 SQL P95 分别为 2.25、3.18、1.97 ms。只加索引时，第二轮实验观测到同一个连接累计使用通用计划从 94 次增至 319 次。按参数规划后该连接的累计次数保持不变。带短局参数的 `EXPLAIN (ANALYZE, BUFFERS)` 中，联合改动通过新索引检查子事件，读到的共享缓冲页从 226 降至 106。真实接口与 SQL 的计时支持保留联合改动。

## 写入开销与回归

- 新索引在约 2 万个事件的读夹具中占 240 KiB。`room_events` 的全部索引从 1,376,256 B 增至 1,622,016 B，增加 17.86%。
- 两轮实验都按原实现、候选、候选、原实现的顺序运行，写阶段每次使用新 schema。每批 500 对问答的 WAL 从 291,610 B 增至 324,370 B，增加 11.23%。批写时间范围重叠，暂未确认写延迟方向。
- 对照检查了历史事件增量为空时的待办读取、待办分页、离席玩家的问题和看底申请、还原正文的可见权限。联合改动在独立 PostgreSQL 中通过 55 个回归测试，其中服务 6 个、迁移 2 个、房间 47 个。包括空库初始化、旧库升级及四项房间规模测试。

本次收益来自合成数据下的单请求对照。接口 P95 未包含公网往返，样本没有测定最大吞吐量或线上读写比例。上线后结合慢查询和 WAL 指标验证收益是否持续。
