# 第 503 条 故障处置手册

当前部署由 Nginx 提供网页和 API 转发，Go 进程通过 Unix socket 连接 PostgreSQL，单人主持另外调用百炼。以下命令在获授权的服务器终端执行。网页私有入口为 `127.0.0.1:18084`，Go 业务入口为 `127.0.0.1:18080`。[服务配置](../../deploy/turtle-soup.service) · [Nginx 配置](../../deploy/turtle-soup.nginx.conf)

## 先确定影响范围

分别检查入口网页、Go 存活和无需登录的公开题目列表。命令只输出状态，便于记录和比较。

```bash
systemctl show turtle-soup nginx postgresql -p Id -p ActiveState -p SubState
readlink -f /srv/turtle-soup/current
curl -fsS --max-time 5 -o /dev/null -w 'web %{http_code}\n' http://127.0.0.1:18084/
curl -fsS --max-time 5 -o /dev/null -w 'go %{http_code}\n' http://127.0.0.1:18080/health
curl -fsS --max-time 5 -o /dev/null -w 'api %{http_code}\n' http://127.0.0.1:18084/api/soups
```

| 现象 | 下一步 | 恢复标准 |
| --- | --- | --- |
| 只有网页入口失败 | 检查 Nginx 状态、当前版本的 `web/index.html` 是否可读，以及故障是否紧跟发布。服务器回环入口成功时，再检查既有 SSH 转发。 | 网页入口返回 200，浏览器能加载首页和所需静态资源。 |
| Go `/health` 失败 | 查看 Go 服务状态、当前版本和启动日志，区分监听、数据库连接与迁移错误。 | Go `/health` 返回 200，公开题目列表通过 Nginx 返回 200。 |
| Go `/health` 成功，公开题目列表失败 | `/health` 只验证 Go 能响应。用 `http://127.0.0.1:18080/api/soups` 对照代理入口，并检查数据库。 | Go 与 Nginx 两边的公开题目列表都返回 200。 |
| 只有 AI 主持失败 | 在后台「运行日志」打开失败请求，查看 Trace ID、HTTP 状态、首个失败阶段与时间线。`ai.model` 指向模型调用，`ai.validate` 指向判定校验，`ai.persist` 指向结果保存。没有失败标记时结合时间线和当时的上游状态排查。 | 使用获授权的测试账号与测试题，正常提问得到合法判定，刷新后仍能读到该结果。 |

根据已定位的组件查看短时间窗口内的日志。故障记录只摘录时间、版本、状态、路由模板、Trace ID 和失败阶段。配置、令牌、Cookie 和玩家内容按服务访问权限留在原处。[链路首个失败阶段](57-链路首个失败阶段.md)

```bash
journalctl -u turtle-soup -u nginx -u postgresql --since '15 minutes ago' -n 80 --no-pager
```

## 数据库与发布

用应用服务账号检查本机数据库。返回 `1` 表示该账号已能连接并执行简单读取，再用公开题目列表确认业务查询恢复。

```bash
sudo -u turtlesoup psql -X -w -v ON_ERROR_STOP=1 \
  -h /var/run/postgresql -d turtle_soup -At -c 'SELECT 1'
```

- 怀疑数据损坏或丢失时，核对受影响的数据范围和备份时点。获准后用持有的私有归档按恢复演练说明验证临时实例，再由负责人决定是否恢复业务库。[PostgreSQL 恢复演练](33-PostgreSQL恢复演练.md)
- 发布脚本切换版本后会探测 Go 与网页。如果探测失败且有上个版本，脚本会尝试切回。确认 `current` 指向预期版本，并重新验收网页、Go 和公开题目列表。若需手动切换版本，先核对已应用的数据库迁移能否与目标应用版本一起运行，由发布负责人执行。[发布脚本](../../deploy/release.sh) · [启动迁移截止时间](24-启动迁移截止时间.md)
- AI 超时、数据库连接失败和房间掉线的复现使用隔离测试库与本地夹具。恢复验收包含玩家可见结果以及重试后的落库数量。[故障注入与恢复](36-故障注入与恢复.md)

## 已启用抓取时的趋势检查

当应用配置了 `METRICS_ADDR` 并已有抓取时，先看五分钟内的请求量，再判断错误比例。图表上缺少样本时回到入口探测和后台链路。项目给出的抓取配置示例使用独立回环端口 `127.0.0.1:18085`，仓库服务配置默认关闭该监听。[Prometheus 运行指标](28-Prometheus运行指标.md) · [HTTP 与数据库查询指标](61-HTTP与数据库查询指标.md)

```promql
sum(rate(turtle_http_requests_total[5m]))
sum(rate(turtle_http_requests_total{status_class="5xx"}[5m])) / sum(rate(turtle_http_requests_total[5m]))
sum(rate(turtle_operation_duration_seconds_count{operation="ai_decision",outcome="error"}[5m]))
```

交接时记录故障起止时间、受影响的入口、失败阶段、已核实的版本、处置结果与恢复探测结果。持续异常时，把这些信息移交给应用、数据库或发布负责人，沿用实际可用的联络方式和权限。

## 隔离演练

使用临时 PostgreSQL 16、回环模型夹具与合成账号连续演练两次。三项测试均通过，耗时为同一用例内的请求耗时，包含测试环境连接开销。

| 请求 | 第一次 | 第二次 |
| --- | ---: | ---: |
| 数据库故障前读取 | 214.6 ms | 209.7 ms |
| 数据库恢复后的写入 | 271.9 ms | 280.5 ms |
| 重放同一次房间写入 | 114.2 ms | 116.7 ms |
| 数据库恢复后的读取 | 147.4 ms | 137.1 ms |
| 模型超时，HTTP 503 | 576 ms | 572 ms |
| 模型恢复后重试，同一个操作 ID | 276 ms | 277 ms |
| 模型成功结果重放 | 73 ms | 68 ms |

数据库断开期间读写均返回 500，恢复后同次提问只保留一条事件和一条操作记录。模型超时阶段没有写入判定事件，成功后重放沿用结果，两轮各只调用上游两次。房间端到端测试也两次通过，覆盖汤底可见性、观众席规则和断线重连。手册提供排查证据，这些数据用于测试环境复现，没有生产 SLA 或告警响应时间推断。
