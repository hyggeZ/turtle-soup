# 对局待办独立于事件历史

## 做法

网页随房间快照请求 `tasks=1`。主持待办按创建顺序显示未答问题、待判还原和待处理的汤底申请，默认最多 50 条，通过 `tasksAfter` 查看下一批。任务游标独立于历史和实时游标。对局暂停时仍可查看待办，处理按钮禁用；回到首批可以重新查看较早仍待处理的事项。

玩家只获得自己是否正等待还原判定或汤底申请结果的两个布尔值。旁观者只获得空待办，旧调用未选择 `tasks=1` 时仍沿用原响应。任务和身份在同一个 PostgreSQL 只读快照读取，沿用答复接口已有的有效性条件。处理完成的事项在下次刷新时移除。

待办列表为进行中房间的历史分页提供前置能力。即使一条待处理事项已早于首屏的历史记录，主持和玩家的控制状态仍有单独的数据来源。

## 本地实测

`TestPendingTasksScale` 使用 Docker PostgreSQL 与同一个 Gin 测试处理器。在每档历史之前插入 3 条仍待处理的事件，交替请求空增量快照和附带独立待办的同一个增量快照。主持和玩家各自预热 5 次、记录 30 次。响应字节按未压缩 JSON，pgx 操作含事务控制语句。

| 已有事件 | 主持 P50，原 → 待办 | 玩家 P50，原 → 待办 |
| ---: | ---: | ---: |
| 103 | 5.29 → 6.10 ms | 5.44 → 5.89 ms |
| 1,003 | 5.12 → 6.80 ms | 5.13 → 6.27 ms |
| 5,003 | 5.49 → 9.03 ms | 5.36 → 7.13 ms |

表内取三轮各自 P50 的中位数。5,003 条事件的快照中，主持响应由 621 B 增至 1,023 B，玩家由 606 B 增至 684 B。主持或玩家附带待办时增加 1 次 pgx 读取操作，总计从 6 次增至 7 次。主持在最大档的待办路径 P50 各轮为 8.32、22.15、9.03 ms。额外读取有实测成本，后续用长对局的分页收益单独对照。当前实现限制返回条数，读取数据库时仍可能扫描历史事件。

```powershell
$env:PENDING_TASKS_SCALE = '1'
go test ./internal/room -run '^TestPendingTasksScale$' -count=3 -v
```

回归覆盖待办页边界、主持实际处理、玩家等待解除、早期待办不依赖增量事件、旁观者的权限隔离和旧快照兼容。
