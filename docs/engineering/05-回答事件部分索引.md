# 回答事件的部分索引

## 问题与选择

房间快照需要判断每个问题是否已有主持回答；增量快照还要把新回答对应的旧问题补回结果。两处查询都按回答事件的 `parent_id` 找原问题，原表只有 `(room_id,id)` 索引。长局测试的 5002 条事件里约一半是回答，改动前全量快照的数据库执行计划每次触发约 156–166 ms 的 JIT 编译。

第 016 版迁移为 `room_events(parent_id)` 建立部分索引，条件是 `kind='answer' AND parent_id IS NOT NULL`。只有主持回答进入该索引；问题、还原和其他事件不增加这项索引写入。PostgreSQL 与原有迁移器仍是唯一数据来源，不增加缓存或额外服务。迁移测试覆盖空库初始化和带已有问答的旧库升级。

## 测量方法

同机 Windows amd64、Go 1.26.5、Docker PostgreSQL 16。改动前后均在独立 schema 运行同一 `TestSnapshotScale`：每轮为 100、1000、5000 条初始事件各追加一组问答；每档预热 5 次、测 30 次，共 3 轮。报告 5002 条事件的 HTTP 快照耗时、响应大小、数据库执行计划和操作数。写入用独立 schema 预置 2500 组问答，再逐条插入 500 条回答，共 5 轮。基线与改动后的原始输出保存在本地 `.local/measurements/016-*.txt`，该目录不入库。

| 指标 | 改动前 | 改动后 |
| --- | --- | --- |
| 5002 事件完整快照 P50，3 轮 | 219.47、261.37、288.52 ms | 45.37、66.56、44.85 ms |
| 5002 事件完整快照 P95，3 轮 | 462.14、841.50、849.84 ms | 116.09、465.51、87.05 ms |
| 完整查询 `EXPLAIN` 执行时间，3 轮 | 172.510、171.861、161.458 ms | 5.764、10.822、5.049 ms |
| 完整查询 JIT 编译总时间，3 轮 | 166.402、163.985、155.798 ms | 未触发 |
| 5002 事件增量查询 `EXPLAIN` 执行时间，3 轮 | 1.561、1.518、1.420 ms | 0.151、0.166、0.157 ms |
| 数据库操作 / 快照 | 6 | 6 |
| 回答写入耗时中位数，500 次 × 5 轮 | 3.798 ms/条 | 4.343 ms/条 |
| 新索引空间，约 3000 条回答 | 0 | 90,112 B |
| `room_events` 全部索引空间 | 360,448 B | 450,560 B |

完整快照的查询计划仍然顺序扫描回答事件；**不能说它通过新索引直接加速了全量扫描**。索引改变估算和计划，使这次负载不再触发 JIT，数据库执行时间因此明显下降。增量快照则实际使用新索引的 Index Only Scan。HTTP P95 受本机负载影响很大，不能从这三轮推出稳定的线上倍数。回答写入的五轮耗时离散，4.343 与 3.798 ms 的中位差也不能单独证明稳定的写入退化。当前线上事件表仅约 10 条，暂不期待现有线上房间立刻出现可测的延迟收益。

## 验收与边界

- `go test ./migrations ./internal/room -count=1` 与 `go test ./... -count=1` 均在真实本地 PostgreSQL 上通过。部署后的版本和健康检查另行核对。
- 迁移器在事务中执行普通 `CREATE INDEX`。线上现有表很小；若未来表变大，这种迁移会在建索引期间阻塞写入，应改用独立的并发建索引流程，不能把 `CONCURRENTLY` 直接放进当前事务。
- 已应用的迁移不通过改写历史回滚。若线上计划或写入成本显示负面影响，应新增下一版迁移删除索引，并保留这份实验记录。
