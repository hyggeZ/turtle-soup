# 第 056 条滑动窗口限流

账号注册、游戏登录、后台登录及房间码查询改用进程内精确滑动窗口。每个键保留最近准许的时间戳，满了就以环覆盖最旧记录。一个请求如果同时受 IP 和账号限制，先在同一把锁内检查全部条件，通过后一起扣减。注册、登录和房间码的原额度沿用，已有房间成员仍可通过原有重连路径进入。发题和评论已有数据库滚动限额。

旧机制以首次请求为起点，到期时重置整窗。候选按每条记录的实际时间恢复名额。同一组固定时钟用例在观察点仍有 4 条有效记录，注册旧版会给出 10 个名额，新版为 6 个，房间查询由 30 个改为 26 个。跨过各自的完整窗口后，两版均恢复正常额度。

两套限流表仍各最多 4096 个键。只有容量不足、并且记录可能已到期时才扫描回收，因此连续被拒绝的请求不会反复扫描同一批记录。时间戳用 8 字节的相对时长，按需扩大环。按各表最大额度估算，活跃环时间戳的容量上界分别为 960 KiB（账号）和 3.75 MiB（房间），另有键和值的头部开销。这是单实例限流。

## 前后对照

在同一台 Windows amd64 机器，Go 1.26.5，对 `d118519` 和候选分别运行相同的内存基准。每项以 100 ms 为目标，执行 5 轮，表中取中位数。没有访问线上服务，也没有将这些数字折算成接口吞吐。

| 场景 | 账号旧 → 新 | 房间旧 → 新 |
| --- | ---: | ---: |
| 稳定流量 | 143.3 → 145.5 ns/op | 158.7 → 144.4 ns/op |
| 多 goroutine 争用已用完的额度 | 125.0 → 133.2 ns/op | 123.7 → 151.6 ns/op |
| 表满且没有到期记录时拒绝新键 | 46,299 → 51.44 ns/op | 44,542 → 96.68 ns/op |
| 表满、旧记录到期后回收 | 213,657 → 125,645 ns/op | 370,471 → 333,862 ns/op |

稳定流量和两类拒绝场景的分配次数相同。回收后首笔请求因初始化时间戳环，账号从 1 次增至 2 次分配，房间从 3 次增至 5 次。房间在高争用拒绝路径每次多耗时约 28 ns。保留候选的依据是按请求时间恢复额度，并显著降低容量满载时重复检查的成本。

## 回归

本地滑动窗口、账号和房间测试均通过。新增用例覆盖精确到期、拒绝后不扣其他规则额度，以及清理后重新计算容量。Linux 上在隔离 PostgreSQL 测试库运行账号和房间测试，50 项通过，4 项按需启用的规模用例跳过。

原始基准与固定时钟夹具在本地 `.local/tech-056/`。
