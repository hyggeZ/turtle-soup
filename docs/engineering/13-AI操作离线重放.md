# AI 操作在模型不可用时重放

## 问题与改动

单人局用 `operationId` 保存已完成的提问和还原判定，客户端超时后可用原操作号取回结果。旧处理顺序在查询已完成事件之前先检查 Qwen 是否就绪；密钥暂缺或模型服务停用时，即使判定早已落库，同一操作仍收到 503。

现在对局事务先锁当前用户的对局行，再按操作号查询已提交事件。若找到且类型、正文一致，直接返回原判定与模型指标；若内容不一致，返回 409。只有**确属新操作**时才检查模型可用性，然后再占用每日额度和 90 秒处理租约。主动查看汤底不需要模型，原有规则保持不变。

## 验收

真实 PostgreSQL 用例先完成一次模拟模型判定，再让处理器使用未配置的 Qwen：

- 原操作号并发重放 8 次均返回 200 和原判定；事件仍只有 1 条，模型尝试记录没有增加。
- 相同操作号但正文不同返回 409；尚在处理的操作返回 409，不会假装已有结果。
- 未配置模型时新操作及释放租约后未完成的原操作返回 503；全局及账号当天调用额度不变，也不留下 `busy_op`。换成可用的模拟模型后，按同一未完成操作号重试成功且只新增一条事件。
- `go test ./internal/agent -run '^TestOfflineReplayWithPostgres$' -count=1` 通过，无真实模型调用。事务内完成重复检查与新操作门禁，避免“先在事务外查重复、再申请额度”之间的并发窗口。

## 开销对照

同机 Windows、Go 1.26.5、Docker PostgreSQL 16，独立临时 schema。预热 10 对请求后，旧版门禁与新版重放交替各执行 100 次，共 3 轮。旧路径复刻上一版的鉴权、参数校验和 `ready()` 门禁；新路径调用真实处理器，两者使用同一已完成操作。计时包含 HTTP 测试处理器及本机数据库访问，不含题目创建和清理。

| 指标 | 旧版 503 门禁 | 新版 200 重放 |
| --- | ---: | ---: |
| P50，三轮中位 | 0.974 ms | 3.552 ms |
| P95，三轮中位 | 3.217 ms | 8.260 ms |
| 业务 SELECT / 请求 | 1 | 3 |
| 新增额度、事件、模型请求 | 0 | 0 |

旧版只查登录会话后拒绝；新版还要查对局和已保存事件。**两者返回结果不同，耗时差额不是同一业务操作的性能回退。**新版完成了旧版无法提供的可恢复结果，且不重调模型、不重复计费。三轮 P50：旧 0.625/1.584/0.974 ms，新 3.552/7.593/3.323 ms；P95：旧 3.280/3.217/1.969 ms，新 8.260/13.274/7.875 ms。本机抖动明显，不能外推到线上；若重放量增长，可进一步测真实网络延迟和数据库连接池等待。
