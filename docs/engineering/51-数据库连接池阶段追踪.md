# 第 347 条 数据库连接池阶段追踪

SQL 追踪在拿到数据库连接后开始。连接池排队时，请求总耗时会上升，已执行的 SQL 耗时却可能很短。取连接失败的请求甚至不会执行查询。原有阶段无法区分这两类情况。

在 Gin 的请求上下文中复用 pgx 已注册的 `AcquireTracer`。`db.acquire` 记录每次取连接的起点、耗时和失败标记，其耗时可能包含池内等待、新建连接和连接检查。仅写这三个追踪信息和固定阶段名。SQL 查询次数和查询耗时另计，原来的字段和计算规则继续使用。[pgx 连接池追踪接口](https://pkg.go.dev/github.com/jackc/pgx/v5@v5.7.6/pgxpool#AcquireTracer)

后台单条请求的「阶段时间线」中显示「数据库取连接」。最近请求的阶段卡将取连接耗时单独汇总，旧日志没有此阶段时正常显示已有数据。连接池拒绝或请求取消可在对应阶段看到失败。阶段之间可以重叠，诊断时应结合时间线，避免把各段时长加成请求总耗时。

## 验收与成本

在隔离 PostgreSQL 16 中将池限制为 1 个连接，通过真实 Gin 路由分别执行正常查询、占用唯一连接后排队再释放、排队时取消。旧方式能看到取连接阶段的场景为 0/3，新方式为 3/3。受控排队样本中，取连接耗时 35.581 ms，执行 SQL 耗时 13.662 ms。排队取消记录了 38.516 ms 的失败阶段，SQL 次数为 0。两种方式均未记录 SQL 语句或错误正文。

用同一个测试二进制交替启用查询追踪和完整追踪。Windows/amd64 各预热 24 个请求，4 对共 1,024 个正常请求，走 Gin、单条实际 SQL 和 JSONL 写入。各组均返回 `204`。下表 P50 与 P95 为各批分位数的中位数。

| 指标 | 仅查询追踪 | 增加取连接阶段 |
| --- | ---: | ---: |
| 正常请求 P50 | 19.710 ms | 19.850 ms |
| 正常请求 P95 | 60.188 ms | 59.306 ms |
| 每条日志平均大小 | 260.717 B | 309.735 B |

各批延迟区间重叠，当前结果无法区分稳定的延迟变化。每条日志平均增加约 49 B（18.8%）。数据库通过 SSH 隧道连接，绝对延迟受网络影响。收益是能单独识别连接池耗时和失败。现有两代日志合计 20 MiB 的轮转上限继续生效。

本地链路追踪竞态检测通过三轮，Vue 测试 24/24。Chromium 跑两轮完整玩家和后台流程及两轮断线补查，共 4/4 通过。后台回归由账号列表请求生成真实追踪，检查日志占用、多个取连接阶段的累计耗时、链路详情逐条显示和弹窗关闭后归还焦点。

设置隔离库的 `TEST_DATABASE_URL` 后，可运行 `go test -v ./internal/telemetry -run '^TestPoolTraceWithPostgres$'` 验证三种情况。若需复测开销，将环境变量 `TURTLE_TEST_POOL_TRACE_PERF` 设为 `1`，运行 `go test -v ./internal/telemetry -run '^TestPoolTraceComparison$'`。
