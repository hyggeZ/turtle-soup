# WebSocket 会话撤销与主持在线状态

## 问题与处理

房间 WebSocket 原来只在握手时检查 Cookie 会话。用户退出登录、管理员停用账号或修改密码并撤销会话后，已经建立的连接仍会响应心跳，最多持续到原有的 30 分钟连接超时。主持人的旧连接还会让房间继续被判断为在线。

现在沿用房间已有的 25 秒心跳，在发送 Ping 前用原 Cookie 重新查询会话、过期时间和账号状态。查询设置 3 秒超时；会话无效、账号停用或查询失败时关闭连接，再使用原有的离线处理：同一主持人其他设备仍在线则保持对局，最后一个连接离线则暂停对局。HTTP 身份检查与心跳检查复用同一处 `SessionUser` 逻辑。

这里用已有的 PostgreSQL 会话表作为唯一状态来源。每次心跳增加一次数据库查询，不另引入缓存，以免撤销后的缓存窗口扩大。查询使用现有连接池，不为每条 WebSocket 独占数据库连接。

## 验收

- 修复前的临时探针已复现：删除会话后连接仍在线，下一次心跳仍可通信，心跳新增 SQL 为 0；该探针不保留在正式测试中。
- 本地 PostgreSQL 集成测试覆盖：正常会话持续连接；撤销一个设备不影响另一设备和对局；撤销最后一个主持会话后房间暂停；停用账号后断连；模拟会话查询失败后断连。
- 本地 PostgreSQL 上 `go test ./... -count=1` 全部通过；`go test -race ./internal/account ./internal/room -run 'TestLiveSessionRevocationWithPostgres|TestLiveDisabledUserWithPostgres|TestLiveSessionQueryFailureWithPostgres' -count=1 -v` 通过。

## 开销与限制

同机本地 PostgreSQL 集成测试中，连续触发 20 次心跳，每次均增加 1 次 SQL。两次运行的平均查询耗时分别为 **1.750、1.007 ms/次**，从测试触发到观测查询完成分别为 **2.934、1.962 ms/次**。后一个数字含测试轮询开销，不代表用户网络往返。两次测试前后连接池总连接数均为 2→2。与旧实现相比，稳定增加的成本是每条在线连接每 25 秒查询一次；若有 1000 条在线连接，理论上约增加 40 次查询/秒，实际承载能力仍需单独压测。旧实现没有这项数据库开销，但无法及时撤销连接，因此保留修复。

正常情况下撤销到断连最多等待下一次心跳，约 25 秒；数据库查询超时时还可能再等待最多 3 秒。数据库故障时会先关闭连接以避免继续使用失效权限，但暂停房间所需的数据库更新也可能失败；服务恢复时已有的 `RecoverActive` 会暂停遗留的活跃对局。该实现只处理会话撤销，不改变房间成员和汤底的权限规则。
