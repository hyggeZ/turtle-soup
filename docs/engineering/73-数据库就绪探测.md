# 第 721 条 数据库就绪探测

Go 进程开始监听前完成迁移和房间恢复。运行期间，`/health` 继续判断进程能否响应，`/ready` 使用当前 PostgreSQL 连接池检查数据库。探测继承原请求的取消信号，最多等待 750 ms。成功返回 HTTP 200，失败返回 503。两种就绪响应均为空正文、不可缓存。

发布脚本切换版本后直接探测回环地址的 `/ready`，仍检查 systemd 状态和网页。三项均成功后确认发布。就绪探测持续失败时，沿用已有回滚。这是单实例发布切换后的检查。[发布产物与回滚](71-发布产物与回滚.md)

| 对照场景 | 原存活探测 | 新增就绪探测 |
| --- | ---: | ---: |
| 数据库可用 | 200 | 200 |
| 连接被拒绝 | 200 | 503 |
| 拨号挂起 | 200 | 503 |
| 数据库连接恢复 | 200 | 200 |

隔离 PostgreSQL 三轮回归共 9/9 通过，12 次存活检查均为 200。三次挂起探测分别在 750.21、751.66、750.77 ms 返回。首次连接用时 98.31–187.49 ms，复连用时 78.12–252.07 ms，包含测试隧道往返。WSL 模拟发布中，服务状态保持活动、20 次就绪探测失败，脚本恢复旧链接及原产物哈希。新检查只在调用 `/ready` 时进行，普通产品请求没有新增数据库操作。

```powershell
go test ./cmd/server -run '^(TestHealth|TestReadinessUsesRequestContext|TestReadinessPostgresRecovery)$' -count=3 -v
```
