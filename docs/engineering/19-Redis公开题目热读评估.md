# 第 009 条 Redis 与公开题目热读

Redis 可以存放频繁读取的匿名题目列表和详情，以减少 PostgreSQL 查询。本站的两个候选入口是没有筛选条件的 `GET /api/soups` 和公开题目详情 `GET /api/soups/:id`。题目列表已有索引和游标分页，首屏最多返回 20 条。

介于鉴权和数据查询之间的缓存，必须区分有凭据和匿名请求。登录用户的收藏、点赞、作者可见状态和汤底由权限决定。公开响应也有会变化的点赞、收藏和评论数。发布、编辑、删除、后台隐藏与恢复都会改变缓存内容。它们成功后须立即反映在下次读取。旧请求在隐藏完成后写回缓存、Redis 超时造成删除失败，都是单用 TTL 或写后删除缓存无法覆盖的情况。

## 测量

基准与[上线回归](18-上线回归与性能基线.md)使用同一个线上版本、服务器回环入口和测试方法。四轮中，每个接口按串行和 4 并发分别采样 12 次，共 192 个题目接口请求。下表列出四轮统计范围，P95 为各批 12 次请求中最慢的一次。

| 接口 | 并发 | 四轮 P50 范围 | 四轮 P95 范围 |
| --- | ---: | ---: | ---: |
| 匿名默认列表 | 1 | 0.943–1.071 ms | 1.070–1.704 ms |
| 匿名默认列表 | 4 | 1.781–2.237 ms | 2.455–13.203 ms |
| 固定公开详情 | 1 | 0.799–0.861 ms | 0.902–1.374 ms |
| 固定公开详情 | 4 | 1.667–1.978 ms | 2.245–3.072 ms |

192 次均成功。在后台取到的首轮样本中，两条路径各执行 1 次 pgx 操作。上线回归另外验证删题后列表与详情立即更新。四轮样本不足以评价大题库或高峰流量，列表也没有持续出现相同的高延迟。

## 结论

本轮暂缓接入 Redis。当前匿名热读未显示出可稳定复现的数据库瓶颈，且缓存失效会影响已下架题目的可见性。数据是现有 PostgreSQL 路径的实测，暂无 Redis 改动后的性能数据。

当访问量或题库规模使数据库查询时间、连接池等待持续上升，再在隔离环境对照 PostgreSQL 与缓存方案。先测冷热命中、请求失败、连接池等待、内存和写后可见性。保留候选方案前应覆盖并发回填与审核下架、Redis 不可用时回源、有凭据的请求不走匿名缓存。
